# Kafka CDC Streams Interview Example

## Interview Scenario
You are capturing changes from an `orders` table in MySQL and publishing them to a Kafka topic named `orders_cdc`.

Source table:

| order_id | customer_id | order_status | order_total | updated_at |
| --- | --- | --- | --- | --- |
| 101 | 9001 | CREATED | 120.50 | 2026-03-16 10:00:00 |

Sample change sequence:
- `INSERT` order `101`
- `UPDATE` status from `CREATED` to `PAID`
- `UPDATE` status from `PAID` to `SHIPPED`
- `DELETE` order `101`

## Strong Interview Answer
For CDC streams, use the source table primary key as the Kafka message key. For `orders`, that usually means `order_id`.

Why:
- all changes for the same row go to the same partition
- per-row ordering is preserved
- downstream upsert consumers can apply changes safely
- compacted topics can retain the latest state per order

Example:
- key: `101`
- value: `{ "op": "u", "order_status": "SHIPPED", "customer_id": 9001, "order_total": 120.50 }`

## Partition-Key Reasoning
Choose:
- `order_id` if the requirement is correct row-level ordering and reliable upserts

Do not choose:
- `updated_at` because the same order would land in different partitions over time
- random UUID generated by producer because it destroys row affinity
- `order_status` because many unrelated rows would collide and ordering for a single order would break

Conditional choice:
- `customer_id` only if the business requirement is to process all orders for one customer in order, and you accept losing strict per-order partitioning semantics

## Topic Design From Interview POV
- Topic: `orders_cdc`
- Partitions: choose based on throughput and consumer parallelism, for example `12`
- Replication factor: for example `3`
- Producer semantics: idempotence enabled
- Consumer semantics: at-least-once by default, with idempotent sink writes or transactions if needed

Important clarification:
- high cardinality primary keys do not create too many Kafka files
- Kafka creates files per partition segment, not per key
- millions of `order_id` values can safely hash across the same fixed set of partitions

## Concrete Example
Suppose `orders_cdc` has `12` partitions.

Kafka hashes the message key:
- `order_id=101` -> partition `7`
- `order_id=202` -> partition `3`
- `order_id=303` -> partition `7`

All events for `order_id=101` keep going to partition `7`:
- insert `101` -> partition `7`
- update `101` -> partition `7`
- delete `101` -> partition `7`

That is the main reason the primary key is the default CDC message key.

## Good Follow-Up Questions And Answers
### 1. Why not partition by `customer_id` instead of `order_id`?
If consumers need per-order correctness, `order_id` is safer because CDC is row-centric. `customer_id` is only better if the use case explicitly requires customer-level ordering and can tolerate skew for heavy customers.

### 2. Does a high-cardinality primary key hurt Kafka performance?
Usually no. Kafka hashes keys into a fixed partition count. The cost driver is partition count, not the number of distinct keys.

### 3. Will Kafka create a file for every `order_id`?
No. Kafka stores data in partition log segments. Keys are logical routing fields, not physical files.

### 4. When do we choose the number of partitions?
Usually at topic creation time. You can increase partitions later, but new records may map differently, so key-to-partition stability across time changes.

### 5. Should a CDC topic be compacted?
Often yes, if consumers care about latest state by key. For full audit history, retention-based topics may be more appropriate than relying only on compaction.

### 6. What happens on delete events?
For compacted topics, deletes are usually represented as tombstones: same key, null value. That lets downstream systems remove prior state.

### 7. How do you handle duplicates in CDC pipelines?
Use idempotent producers on the Kafka write path and idempotent upserts in sinks. Kafka can still replay after failures, so downstream consumers should be designed for reprocessing.

### 8. What if one partition becomes hot?
That usually comes from skewed write patterns, not from high cardinality itself. You may need more partitions, workload isolation, or a different topic design if a few keys dominate traffic.

## Fast 30-Second Interview Answer
For a CDC Kafka stream, I would usually use the source table primary key as the message key, such as `order_id` for an `orders` table. That keeps all changes for the same row in one partition, preserves row-level ordering for insert, update, and delete events, and works well with compaction and downstream upserts. The number of Kafka files depends on partitions and segment rollover, not on primary-key cardinality.
